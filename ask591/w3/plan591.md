## 2. What is true now (source: engine manual v279 parts 02.0, 04.0, 10.0, 17.0, read by SQL this turn; repo a482_w1; NOT read by W3: the engine code)
1. The order is code. Init Seats holds `ORDER0` (one list of judge seats) and `__ALT` (the seats that are alternates only). The panel is the first three free seats, the reserve is the next, the alternates follow in `ORDER0` order (part 10.0, "How seats are drawn").
1a. Init Seats is not the start of the run (W1's read of live 9bec145c, Wall 11414): its parent chain is Accept Models, Accept Build, Accept Call openrouter (the judges' agreement, which makes model calls), Accept Check, Accept Return?, Accept Final, and only then Init Seats. Init Seats also uses `ORDER0` for the agreement (AGREE_OUT). `ORDER0` and `__ALT` stand only in Init Seats; Accept Build holds a second copy of the order (`ORDER`), which it uses to ask the judges' agreement of every seat that is not a debater and not qwen. Pass Accumulate holds no `__ALT` (W4's read; the text W1 saw there is `__ALTL`, a function that writes the ALTERNATE TRIED line); it takes the alternates from Resolve Seats, which takes them from Init Seats (`S.alt_order`). No other node, no child node and no Shared Library line holds a seat list in this order.
1b. The live order (W4's read): `ORDER0` = chatgpt, sol, sol62, haiku, gemini, spark, qwen4max, argon, sonnet. `__ALT` = haiku, gemini, spark, qwen4max, argon, sonnet. The start paths are Debate Start (webhook) then Library Check, or Manual Start then Dry Run Config; both reach Accept Models, Accept Build, the agreement calls, Accept Final, Init Seats. A regrade enters through Debate Start.
2. The same order stands in other nodes: Accept Build, and seat or family maps in Resolve Seats, Build Synthesis, Build Independent Verdict and Build Diagnostic Prompt (part 10.0, "JUDGE ORDER AND ALTERNATES, LIVE AS OF ASK 437"). A change of order today is a hand edit of several nodes.
3. Rules that act on the order and are not the order itself: the family rule (FAM_PANEL); NOT_PANEL (the time rule, ruling 362; deepseek, ruling 421); posture acceptance; the judge fault ledger's move of a seat to the end at state ALTERNATE; the seated-debater rule; the Claude exception; guards G1 to G3 and G5 on alternates; the database functions odv1_record_panel_alternates and odv1_record_panel_substitution, which admit or refuse seats by their own tests and lists.
3a. A RULE THE MANUAL DOES NOT STATE (W4's read of Init Seats): after the first three free seats, haiku is moved to the end of the rest. So today haiku, fourth in `ORDER0`, is not the reserve in the usual debate; gemini is. I searched manual parts 10.0, 17.0 and 17.1 and md_notes_rulings for this rule and found no line that states it and no ruling row that orders it. See section 5A.
4. The single judge, and so the synthesis and the diagnostic, is the first free seat of the order that is not time-removed, not of a debater's family, and not haiku or sonnet (the single_judge filter of Init Seats; W1's read of live 9bec145c). A change of order can change the single judge, but it never makes haiku or sonnet the single judge.
5. The dashboard is a static site on the Vercel project truth-app-dashboard. Its pages are JavaScript files that call database functions (dash_api and the dash_ functions). ASK 482 is the precedent: SQL functions plus deploy/src/odv1.js, deployed by a seat. The debater list already comes from the database (dash_debaters), and the launcher reads it.

## 3. The objective
The operator opens a dashboard page, puts the panel judges and the alternates in the order he wants, saves, and the next run seats judges in that order. No model edits engine code to change the order. The page shows him the line-up a run will seat, after the engine's rules.

## 4. The design
S1. ONE TABLE, the one home of the order: `odv1_judge_order` (seat text primary key, references model_config.seat; list text: 'panel' or 'alternate'; ord integer; unique (list, ord)). And `odv1_judge_order_log`: one row per save, holding the whole order before and after, the time and who saved. RLS on. Seeded in the same migration from the live `ORDER0` and `__ALT` as W4 reads them at build, so the first run after the write seats exactly what it seats today.
S2. READ FUNCTION for the engine: `odv1_judge_order_read()` returns the two lists in order and a version number (the log row id). EXECUTE for service_role and lab_seat only, as record_debate_row_tokens.
S3. THE ENGINE READS IT AT RUN START. A code node cannot query the database, so one new read node (the same credential and node type as the engine's other rpc calls) calls odv1_judge_order_read. It stands between each start path and Accept Models (W4's R2), and so BEFORE Accept Build on every start path (F1), so that the judges' agreement and Init Seats both use the table's order. Accept Build takes the order, and Init Seats takes the order and the alternate set, from that item in place of the constants `ORDER`, `ORDER0` and `__ALT`. Resolve Seats and Pass Accumulate already follow Init Seats and do not change. Every other node that holds its own copy of the order (item 2.2) reads Init Seats' output instead of its own copy; W4 names each in the build. The rules of item 2.3 are NOT changed: they act on the table's order exactly as they act on `ORDER0` today.
S4. THE ORDER A RUN USED IS RECORDED: Init Seats' output carries the order version, and Build Save Body writes one review_notes line "[JUDGE ORDER v<n>: panel list ...; alternates ...]". (Build Save Body runs after Init Seats, so the line writes; W4 confirms on the live path, the lesson of Wall 11403.)
S5. IF THE READ FAILS or the table does not pass the checks of S7: the run stops at the read node, which stands before Accept Build and so before any model call (F1), with the message "JUDGE ORDER: the order table could not be read (<reason>); no call was made". Reason for stopping and not falling back: a run that silently used an order the operator did not set would be a result he did not ask for, and stopping before any call costs nothing. The launch status on the dashboard shows the message.
S6. A run reads the order once, at its start. A save during a run changes the next run, not the running one. A REGRADE DOES NOT KEEP THE SEATS OF THE RUN IT REGRADES (W4's R4; rev 1 was wrong here): it passes through Accept Build and Init Seats and draws its panel from the order as it stands at the regrade. This is how the engine works today with the order in code; ASK 591 does not change it. Keeping a run's original seats on its regrade would be a separate change.
S7. SAVE FUNCTION for the page: through dash_api (the dashboard password), action `judge_order_save` with the two lists. It refuses, and changes nothing, unless: every seat of the table is in exactly one list, once; no seat is added or dropped (a new model still needs its model_config row, its check call and its engine maps first: a separate ASK each time); the panel list holds at least four seats that are active in model_config. It writes the table and one log row in one transaction.
S8. THE PAGE (a new tab, "Judge order", on the dashboard): two lists, PANEL JUDGES and ALTERNATES. Each row: position, model name (the odMName rule), model id, family, active or not, and the fault ledger state (COUNTING, EXAMPLES, ALTERNATE) from jfl_report. Drag, or up and down buttons, within a list and between the lists. A Save button; after a save the page reads the table back and shows it. Below: THE LINE-UP FOR A DEBATE. He picks defender and challenger (the dash_debaters list) and the page shows panel 1 to 3, the reserve, the alternates in order, the single judge, and every seat left out with its reason in words (same family as a debater; removed by the time rule; moved to the end by the fault ledger; is a debater). One line states what the page cannot know before a run: whether each seat accepts the posture.
S9. THE LINE-UP SHOWN IS COMPUTED BY ONE SQL FUNCTION, `dash_judge_lineup(def_engine, ch_engine)`. This is a second copy of Init Seats' drawing rule, which is a risk: two copies can drift. The function takes every input that Init Seats' drawing uses, each from the same source as the engine (F2): the order table, NOT_PANEL, FAM_PANEL, the seated debaters, the fault-ledger move (jfl_move, which the engine takes from Accept Models at run time), the time rule, the alternate guards, the Claude exception, the single judge's filter (no haiku, no sonnet), and the haiku rule of item 2.3a as the operator decides it (section 5A). W4's list from the code is in read591_notes.md R1 item 5. AGREE_OUT (the seats that did not accept the posture) is known only in a run; the page says so. The control: test T2 below compares the function with Init Seats for every ordered debater pair and varies each of those inputs; and every live run's S4 line records the panel, reserve, alternates and single judge as seated, so any drift from the page shows in the record and the AAR compares them. T2 is rerun at every later change of Init Seats (added to part 15.0, Verifying a change). The page says "as the engine would seat it now".
S10. NOT CHANGED: the family rule, the time rule, the fault ledger, the guards, both recorder functions and their bars, model_config, every prompt, every judge rule. No reasoning text is touched. The display order in dash_odv1_debates and dash_odv1_judges (a seat list without sol, part 17.0) is a display matter and is out of this ASK.

## 5. Limits stated plainly (for the card)
L1. The page reorders seats the engine already knows. It does not add a model.
L2. A seat of the ALTERNATES list sits on the panel only when fewer than three PANEL seats are free (W1's N1); the page says so beside the lists. The rules of item 2.3 still decide who sits. A seat he puts first can still be left out by the family rule, the time rule or the fault ledger; the page shows that before the run.
L3. The reserve recorder (odv1_record_panel_substitution) keeps its own seat list, and qwen4max is not on it (W4's R3). An order that makes qwen4max the reserve would fail at the reserve's record. The save function refuses an order whose possible reserve (any seat that can stand fourth for some debater pair) is not on that list, and names the seat; today that means qwen4max cannot be put where it could stand fourth. Changing that list is not in this ASK.
L4. A changed order can change the single judge (item 2.4). Haiku and sonnet are never the single judge, whatever the order.
L6. A save between a run and its regrade changes the regrade's panel (S6).
L5. Anyone who holds the dashboard password can change the order (W1's N1). Every save is in the log table with its time.

## 5A. One question for the operator: the haiku rule (item 2.3a)
With the rule kept, haiku goes behind the other seats whenever it is not one of the first three, whatever order the page holds; the page would show that. With the rule removed, haiku sits where the saved order puts it, like every other seat. The starting table is then written with haiku last, which seats the usual debate exactly as today; debates where an OpenAI model debates would seat differently from today (there the first three free seats now include haiku), and test T1 names every pair that differs. The record I read does not show where the rule came from, so I cannot say whether removing it reverses a ruling. His choice, on a card.
